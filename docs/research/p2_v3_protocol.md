# P2 V3 engineering execution boundary

The user authorized P2 on 2026-10-28. P2-A is a new, single-condition `positive_high` engineering Study and independent Store. It starts from an ordinary symmetric V3 generation request and a uniform 0.2 N control seed, without importing a historical candidate or successful control. The task, floor, payload, physical constraints, time window, and acceptance thresholds are unchanged.

Aggregate P2 ceilings across every Store are 8 Provider requests, 32 public operations, 5 mathematical entries, at most 3 T1 attempts with at most 51 callbacks each, 1 independent physical replay, and 600 numerical seconds. The initial P2-A grant is strictly smaller: 0 Provider requests, 12 public operations, 3 mathematical entries, 0 replays, 240 numerical seconds with 30 seconds held back and a 180-second maximum worker timeout. The explicit `bounded_worker_v1` guard is an opt-in worker safety boundary layered over the unchanged count-mode ledger; it does not pretend the existing count-mode `budgets.numerical_s` is enabled. Numerical use remains charged by the original Store. The margin reserves time for non-worker preparation and controlled shutdown; unknown worker termination forbids a relaunch. It is not a real-time operating system guarantee.

Run only one initial T1. Further attempts require inspecting the actual receipt, a specific diagnostic distinction, the original unchanged Store, and the remaining aggregate limits. Any subsequent P2-B must have an independent empty Store and its frozen grants must be no larger than the aggregate remaining after all prior P2 costs; it cannot inherit P2-A candidates or evidence. There is no automatic retry or P3 execution. If P2-A cannot produce a finite full-window result, P2-B is not run.

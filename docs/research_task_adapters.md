# Research task adapters and offline acceptance, version 1.0.0

The first study uses `tools/research_tasks.py` as the shared task entry point. Its adapter selects the registered output, reference, operating point, metric meanings, task context and lifecycle rules. The assembler remains responsible for evidence identity, permissions and budget; numerical kernels remain responsible for numerical calculations. No historical evaluator, report, script, or sealed campaign is redefined.

`task_adapter(effective_or_saved_configuration)` accepts a `SessionInput` or saved candidate configuration. `describe()` exposes task/reference/signal contracts and metric units. `reference_at(times)` delegates timed tracking to the existing Cartesian-reference implementation and gives a constant reference for reach. `operating_point(time_s)` describes reference position and velocity; it does not claim an equilibrium or replace the actual task initialization. `check_compatibility()` checks the registered controller/backend combination separately from matching historical experiments. Technical support is not validation evidence.

The stable first-study pairing is `task.reach@1.0.0`, `evaluate.reach@1.0.0`, `controller.gvs_nmpc@7.0.0`, `model.serial_bending_cells@1.0.0` and `backend.family_mujoco@1.1.0`. Existing tracking uses `task.tracking@1.0.0`, `evaluate.tracking@1.0.0` and `controller.gvs_nmpc@5.0.0`; its length-only envelope and timed reference remain authoritative. Tracking with controller v7 is explicitly unsupported: v7 owns reaching and does not implement the tracking reference/control contract. The adapter never substitutes reach scoring for tracking.

## One result for evaluation, ranking, stopping and reporting

`assemble_acceptance(configuration, evaluation, profile, evaluation_reference=..., profile_reference=..., motion=...)` consumes the sealed evaluator output and `control.profile_report` detail. Callers load these from the existing artifact store and preserve their references in the returned `research.task_acceptance@1.0.0`. The result checks available task, execution-scope, simulation and evaluation bindings. It retains every evaluator constraint, evaluator validity, execution completeness, task success, solver-error count and force violation. The evaluator continues to own terminal-position success; the composition owns the new offline joint acceptance.

The default protocol identity follows task semantics: `offline_reach_hold_v1` for reach and `offline_tracking_v1` for timed tracking. An explicit protocol identifier may be supplied for a separately declared study; task family and task identity remain visible and are checked when comparing results.

For the first study joint acceptance requires a valid complete execution, evaluator success, zero solver errors, input-bound compliance, and covered final-window position and speed compliance. The existing numerical force tolerance is `1e-8 N`; configured tendon limits remain physical input constraints. Holding limits and window are read from the frozen effective controller configuration and must match the sealed report. The first specification freezes `0.05 s`, `0.01 m` and `0.02 m/s`. Both endpoints and the inclusive uniform sample grid are required. The sealed report's `sampled_settling.available` is its existing coverage authority. If callers provide sealed motion, the composition additionally checks every final-window timestamp. Speed remains the existing world tip Jacobian-times-recorded-velocity reconstruction, not finite differences. No continuous-time guarantee is implied.

The mutually distinguishable result states are `accepted`, `valid_failure`, `missing_evidence`, `incomplete` and `invalid`. Unknown acceptance is `None`, never fabricated `False` or `True`; individual known failures remain visible even when another component is missing. Terminal-position success cannot substitute for holding success. Contradictory source bindings or holding definitions produce `invalid`.

The new offline result does not require real-time deployment. Control period, sampling, duration, solver stopping and computational limits are unchanged. Deadline misses, update time and total execution cost remain diagnostic fields. Historical protocols keep their original real-time failures; this result is only for the new offline protocol.

`compare_acceptance(candidate, incumbent)` first compares joint acceptance, then compares the applicable physical metrics component by component. Opposite-direction changes are a trade-off. Required missing metrics yield unavailable comparison; computation and controller scalar objectives cannot hide physical deterioration. Direct results must have matching task/protocol identities. Aggregates must share task family, protocol and frozen schedule identity. Conditions changed between a historical run and a smoke test permit separately labelled descriptive deltas, not a matched research improvement claim.

`aggregate_acceptance(records, scheduled, schedule=...)` uses the frozen scheduled denominator. Each record names `case_id`, `seed`, `repetition`, `acceptance` and the simulation `receipt`. All slots remain in the denominator, including pending, failed, incomplete and replayed slots. Counting an accepted repetition requires a distinct simulation execution, `cache_hit: false`, one charged backend solve, and matching acceptance execution identity. Reusing a receipt or cached output is not a repetition. Duplicate schedule slots and unscheduled repetitions are rejected. Primary output is observed joint acceptance divided by scheduled repetitions; maximum applicable physical errors/speed are separate secondary metrics. A small deterministic case set does not establish a population success probability.

`stop_interpretation(result, reason, budget_exhausted=..., remaining_work=...)` consumes that same result. It exposes stop legality separately from supported success and leaves stop optimality unassessed. Legal declared reasons are exhausted budget, completed scheduled work or a predeclared policy. Budget is an upper bound. A local successful execution does not prove an unexecuted perturbation suite successful; use its aggregate for study claims.

## Initialization, cache and recovery

Each new execution uses isolated controller/backend instances, resolves the candidate robot, and applies every named initial position and velocity exactly once. No retry-to-pass initialization, velocity zeroing or reinterpretation of generalized coordinates is added. The first-study specification supplies the normalized bend/rate mapping; the task adapter consumes its resulting named initial state. Warm predictor states are regenerated from measured states; compatible historical tensions remain numerical guesses, not execution evidence.

The registry declares GVS controller reset and restore unsupported. In-place controller reset and continuation from a partial physical/controller checkpoint remain unsupported. Research process recovery restores Store evidence, budgets, completed slots and pending work; an unfinished physical attempt is retained, and subsequent work creates a distinct execution according to the declared schedule. Repeated request IDs return the original receipt. Independent scheduled repetitions require a fresh request ID and `cache: new`; changing robot, initializer, timing, reference or control invalidates candidate-dependent execution reuse.

## Focused validation

`python -m unittest tests.test_research_tasks` checks endpoint success with failed holding, missing coverage versus incomplete execution, source/definition mismatches, exact holding-grid coverage, replay exclusion, separate cost and physical trade-offs, and legal stopping versus supported claims. The task interface check exercises registered tracking evaluation on a synthetic declared signal grid and compares constant reach with a changing quintic reference; it also exposes the unsupported v7/tracking pairing. It does not simulate a second campaign or validate physical tracking performance. The fixed-baseline integration report separately records actual backend validation.
